# MetaYoshi

Non-custodial Raptoreum (RTM) browser-extension wallet for Chromium and Firefox.
It holds RTM and Raptoreum assets (fungible and unique) and talks directly to an
[ElectrumX for Raptoreum](https://github.com/peppez07/electrumx-RTM) server.

- Keys never leave the browser. The recovery phrase is stored encrypted
  (PBKDF2-SHA256 + AES-GCM) and is only decrypted into memory while unlocked.
- Transactions, including asset transfers, are built and signed locally.
  The server only sees script hashes and the signed transaction.
- Addresses: BIP44 `m/44'/175'/{account}'/0/0`, P2PKH (`R…`). These match the
  addresses created by earlier MetaYoshi releases.

## How it works

```
popup (React)                                  ElectrumX for Raptoreum
 ├─ src/lib/rtm/        keys, scripts, tx      ┌───────────────────────────────┐
 │   address.ts         BIP39/BIP44, R… addr   │ blockchain.scripthash.*       │
 │   assetScript.ts     asset transfer scripts │ blockchain.scripthash.assets.*│
 │   transaction.ts     serialize + sign       │ blockchain.asset.get_metadata │
 │   builder.ts         coin/asset selection   │ blockchain.transaction.*      │
 ├─ src/lib/electrum/   public JSON-RPC HTTPS gateway (or WebSocket)        │
 └─ src/store/          wallet state (zustand) └───────────────────────────────┘
background service worker: routes dApp requests to the popup, never signs
```

On connect the wallet checks the server's genesis hash and refuses any server
that is not Raptoreum mainnet. Asset features wait for the server's
`rtm_assets.ready` flag.

## ElectrumX server requirements

The default endpoint is `https://144.202.18.233/api/v1/electrum`. It accepts
public Electrum JSON-RPC over HTTPS and requires a browser-trusted TLS
certificate. No Core RPC credentials or server password belong in the wallet.
The gateway forwards public requests to a private Electrum connection; it
cannot sign transactions. The wallet sends no cookies and refuses redirects.

HTTPS subscriptions poll every 15 seconds and report changed header, address,
and asset statuses. A random session token preserves server-side pagination
across requests; it contains no wallet key or password. A synchronizing server
shows a waiting message and the unlocked wallet reconnects automatically.
Transaction broadcasts are attempted once, including when the server asks to
retry. If submission is unconfirmed, check the transaction status before
sending again.

Existing `wss://` Electrum servers remain supported. Explicit `http://` gateway
and `ws://` URLs are available for local testing only. URLs containing
credentials or fragments are rejected. Certificate validation remains enabled.

Install the HTTPS gateway using the ElectrumX repository's
[wallet HTTPS instructions](https://github.com/peppez07/electrumx-RTM/blob/master/docs/wallet-https.md).
The public server needs inbound ports 80/443 for certificate issuance and
HTTPS. The endpoint becomes usable after installation and chain indexing.

The previous built-in `wss://144.202.18.233:50004` entry is migrated to HTTPS
on startup. Custom server entries and active selections are preserved. Change servers in
**Settings → ElectrumX servers**, or set the build default:

```bash
VITE_RTM_ELECTRUM_SERVERS="https://node1.example/api/v1/electrum,wss://node2.example:50004" npm run build
```

The wallet tries the active server first, then the others in order.

### Server discovery

The wallet needs no single server. Each HTTPS gateway publishes
`/api/v1/servers`: gateways it found and verified among the registered Raptoreum
smartnodes, using its own Core node. After connecting, the wallet merges these
lists (refreshed every 30 minutes, kept up to 7 days) and tries those servers
after your own, so it keeps working if the built-in server is down.

Discovered servers are only candidates. Each must pass the genesis check, and
the wallet compares a recent block header with another server. If every
reachable server disagrees, the wallet shows a warning and refuses to sign or
broadcast until you choose another server. Keys, signing and the recovery phrase
stay in the browser; servers only see script hashes and signed transactions.
Turn discovery off in **Settings → ElectrumX servers**.

## Develop

```bash
git pull --ff-only
npm ci
npm test               # unit tests and mock ElectrumX tests
npm run lint
npm run build          # dist/ (load unpacked in chrome://extensions)
npm run build:browsers # dist-chromium/ and dist-firefox/
```

For Chromium, run `npm run build:chromium`, enable Developer mode in
`chrome://extensions`, and load `dist-chromium/` as an unpacked extension.
After an update, rebuild and reload the existing extension to retain its
stored wallet. Keep the recovery phrase backed up before updating.

Tests cover the derivation addresses from earlier releases, asset scripts
generated by the ElectrumX test suite, real mainnet signatures (block 20000),
coin and asset selection, and both transports against local HTTP/WebSocket
servers (session continuity, polling, cancellation, protocol errors, and one
broadcast attempt).

To check a real server (read-only: features, balances, history, assets, fees):

```bash
RTM_LIVE_SERVER=https://144.202.18.233/api/v1/electrum npm run test:live
```

`RTM_LIVE_ADDRESS` selects the address to query.

## dApps

See [docs/SDK.md](docs/SDK.md). The provider is `window.metayoshi`
(alias `window.rtm`), with `wallet_sendTransaction` and `wallet_sendAsset`.

## Status

Beta. Coin and asset sends still need live mainnet testing; use small amounts.

- Unique-asset sends that split a token range follow the server's range model
  but have not yet been confirmed on mainnet.
- Message signing is not implemented.
